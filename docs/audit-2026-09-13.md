### F01 · 备份“保护”可绕过，内容直接可读

位置：[BackupManager.kt:108](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/backup/BackupManager.kt:108)、[BackupManager.kt:133](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/backup/BackupManager.kt:133)、[BackupRestoreViewModel.kt:150](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/ui/viewModel/BackupRestoreViewModel.kt:150)。

密码和图案只被计算为 SHA-256 并放入 `meta`；设置、漫画名称、标签和章节等数据直接序列化到 JSON。恢复步骤只检查 `meta.protectionType`。拿到备份文件的人无需密码就能查看数据，把该字段改为 `none` 还能正常进入恢复。选择“密码 + 图案”同样如此。无盐快速哈希还允许对短 PIN 离线枚举。

**影响范围：获得导出备份文件的人。不是远程读取应用私有存储。** 备份确实剔除了应用锁密码和图案，但没有加密其他备份内容。

建议引入带随机盐、密码派生和认证加密的新格式，保护整个内容及必要元信息；旧格式明确标为未加密。若产品只需要恢复前确认，应撤掉会让用户误认为文件受密码保护的表述。

复现：`protectedBackupIsPlaintextAndMetadataBypassesVerification`。

### F02 · 暂时读不到设置时，应用锁按关闭处理

位置：[LocalSettingStorage.kt:40](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/storage/LocalSettingStorage.kt:40)、[LocalSettingManager.kt:381](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/storage/LocalSettingManager.kt:381)、[App.kt:88](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/App.kt:88)。

底层正确区分了 `TemporaryUnavailable` 与不存在，但 `LocalSettingStorage.load()` 把暂时不可读转换成 `null`；管理器只在初始化时读取一次，因此保留 `LocalSetting()`，其中应用锁关闭。Keystore 恢复可用后，管理器也不会自动重读。新手引导可能重新出现，完成引导后会按当前无锁状态进入应用。

建议将“尚未成功读取安全状态”与“确认未设置锁”区分，加载失败时保留受阻界面并提供重试；不要继续用无锁默认值，也不要在此期间写回默认设置。

复现先保存启用的锁，模拟密钥提供者暂时异常；旧管理器一直显示未启用，新建并成功读取的管理器则显示已启用。

复现：`temporaryReadFailureDisablesLockAndDoesNotRetryInManager`。

### F03 · 安全设置写入失败没有反馈，界面与重启后的状态不同

位置：[LocalSettingManager.kt:375](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/storage/LocalSettingManager.kt:375)、[LocalSettingStorage.kt:57](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/storage/LocalSettingStorage.kt:57)。

管理器先更新内存并通知 UI，再持久化。存储把 `TemporaryUnavailable` 转为 `Unit`，上层无法知道保存失败。用户设置密码并开启锁后，当前界面显示开启，但重启仍读取之前的关闭状态；没有重试队列或失败提示。

建议写接口返回可辨别的结果。安全设置在确认持久化成功后再发布成功状态；失败时保留旧状态并提示重试。普通设置可以乐观更新，但也需要明确的失败恢复机制。该问题与 F02 分属读、写两条路径，修复其中一条不会解决另一条。

复现：`failedLockWriteLooksEnabledButRestartsDisabled`。

### F07 · 批量删除历史可能在切换账号后继续删除

位置：[UserViewModel.kt:135](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/ui/viewModel/UserViewModel.kt:135)、[UserRepositoryImpl.kt:133](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/repository/impl/UserRepositoryImpl.kt:133)、[UserManager.kt:130](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/session/UserManager.kt:130)。

`deleteHistoryComics()` 循环逐条调用仓库，没有在批次开始时捕获账号和会话代次。“历史”页面使用 Activity 范围的 `UserViewModel`，离开页面不必然取消任务。底层请求执行器只为每次调用捕获当时的会话。

触发条件：A 发起多条删除，用户离开页面并切换到 B，切换落在两次请求之间。后续请求可捕获 B 的会话，继续提交 A 批次剩余的漫画 ID；若 B 存在相同历史记录，会操作到 B。单次请求的会话校验并不能约束整个批次。

建议参考收藏批量操作：捕获一次会话快照，整个批次使用该快照约束每次远端操作，并在账号变化时停止。此结论来自静态时序分析，未对真实账号执行删除验证。

### F04 · 严格映射没有处于受控异常边界内

位置：[ComicRepositoryImpl.kt:64](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/repository/impl/ComicRepositoryImpl.kt:64)、[NetWorkResult.kt:42](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/core/network/NetWorkResult.kt:42)、[ResponseMappers.kt:60](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/data/comic/mapper/ResponseMappers.kt:60)。

仓库在数据源已返回 `NetWorkResult.Success` 后执行 `.map { ... }`，而 `map` 不捕获转换异常。空白／非数字漫画 ID 等异常字段会让 `toInt()` 直接抛出。分页 `load()` 同样没有异常转换，异常越过 `LoadResult.Error`，可能导致列表加载任务失败或未捕获异常，而不是正常的错误／重试 UI。详情和首页也存在同类边界。

建议保留协议字段严格解析，将映射放进仓库的受控错误边界，明确返回解析错误并保留原因；协程取消继续抛出。不要用 `toIntOrNull() ?: 0` 把畸形 ID 伪装成有效数据。

复现使用包含空 ID 的成功响应，直接调用真实仓库与真实 `SearchComicPagingSource.load()`，得到 `NumberFormatException`，没有得到 `LoadResult.Error`。

复现：`malformedWireItemEscapesRepositoryAndPagingErrorContract`。

### F08 · 索引写失败后，任务看似完成且无法通过自动重试修复

位置：[DownloadContentOperations.kt:121](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/download/molecule/DownloadContentOperations.kt:121)、[DownloadComicCoordinator.kt:73](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/download/coordinator/DownloadComicCoordinator.kt:73)。

`complete()` 先更新路径和 `COMPLETE`，再写 `config.json`。磁盘满、目录权限变化或文档提供器失败会使索引写入抛出。协调器准备重试，但下一次执行看到 `COMPLETE` 立即返回成功，不再补写索引。

图片可能仍可通过数据库读取，因此不能把后果夸大为所有漫画无法阅读；确定的问题是完成状态与落盘结果不一致，索引、通知与批次收尾可能缺失。

建议先完成可失败的文件写入，再提交最终状态；若需先生成最终元数据，可在内存构造完成态快照。否则应保留明确的“待提交／待补写索引”状态，允许重试。

复现：`configFailureLeavesCompleteAndRetrySkipsWritingConfig`。

### F09 · 更新下载取消回调注册在错误的生命周期阶段

位置：[AppUpdateDownloadManager.kt:137](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/update/AppUpdateDownloadManager.kt:137)。

代码声称要解除 `InputStream.read()` 阻塞，但用的是普通 `job.invokeOnCompletion`。它等待任务完成；任务正在阻塞读取时，单纯取消协程不会让这个回调立即运行。界面可以先显示取消，新下载仍等待旧写入者释放互斥锁，实际停止依赖网络返回或读取超时。

建议保存并直接取消当前 `Call`，或用可取消的网络挂起适配，在取消时调用 `Call.cancel()`，继续保留单写入者互斥。普通完成回调与取消回调的区别参见 [Kotlin 官方文档](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-job/invoke-on-completion.html)。

复现：`completionHandlerCannotUnblockRunningBlockingRead`。运行验证了相同回调与阻塞体的语义；未对 Android 更新 UI 做弱网端到端验证。

### F10 · 系统备份遗漏新加密存储文件

位置：[backup_rules.xml:4](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/res/xml/backup_rules.xml:4)、[data_extraction_rules.xml:5](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/res/xml/data_extraction_rules.xml:5)、[SecureStorage.kt:134](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/storage/SecureStorage.kt:134)。

建议同步排除新文件，并明确普通偏好、账号凭据与设备安全状态分别如何恢复。未做系统备份真机实验。

### F12 · 外部输入的大小限制发生过晚或缺失

位置：[BackupManager.kt:205](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/backup/BackupManager.kt:205)、[EmbeddedComicDataSource.kt:419](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/data/comic/EmbeddedComicDataSource.kt:419)、[ReaderSourceLoader.kt:171](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/reader/molecule/ReaderSourceLoader.kt:171)。

## 架构、可读性与过度防御

**A01 · 仍有一条真实的底层到入口依赖环，需要优先于机械拆文件处理。**

代码链为 `storage → utils → MainActivity → ui/theme → storage`。通知工具 [AppNotifications.kt:16](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/utils/AppNotifications.kt:16)直接依赖入口 Activity；[MainActivity.kt:15](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/MainActivity.kt:15)依赖主题；[GTheme.kt:22](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/ui/theme/GTheme.kt:22)依赖设置。修正根文件节点命名后，import 图的这个强连通分量包含 `MainActivity.kt / launcher / storage / ui/theme / utils`。

这违反项目所声明的底层不得依赖入口方向。建议把具体通知 Intent 的创建放到平台适配器或组合根，底层使用通知端口／Intent 工厂。不要因整个 `utils` 包被视为 L4，就把 Activity 依赖也当成原子能力。

同一次扫描还得到 reader 各分包、Retrofit 与其 converter/interceptor 的强连通分量；其中包含共享类型与实现协作，不能仅按包级 SCC 就断言每条都是业务环。需要按类和契约判断。

**A02 · 架构指标和边界测试有盲区。**

[check-coupling.py:51](/Users/utolaris/Documents/ai/jmcomic-plus/scripts/check-coupling.py:51)把根源文件记为 `MainActivity.kt`，但其 import 目标记为 `MainActivity`，将同一对象拆成两个节点；全限定类型使用、同包调用也不在 import 统计中。因此当前耦合表不等价于完整依赖图。`ArchitectureBoundaryTest` 是列举禁止前缀的回归测试，不是完整的四层规则检查；指定路径不存在时还会返回空结果，旧路径检查容易静默失效。

建议统一符号与模块映射；对必须存在的边界路径增加存在性校验；由一份规则同时生成 import／全限定使用检查，避免两份列表分别维护。现有边界测试有价值，应保留，不能把“全部通过”解释为无循环、无跨层依赖。

**A03 · 存在可以直接消除的无效间接层。**

[Retrofit.kt:67](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/retrofit/Retrofit.kt:67)的 `clearCookie()` 已是空操作，客户端本身使用 `CookieJar.NO_COOKIES`，但 `UserManager` 仍通过 `ActiveSessionCookieStore` 持有它并在退出时调用。这个接口已不承载真实能力，还让会话层继续依赖 Retrofit。建议删除这条空操作依赖，保留真实 Embedded 会话清理。

仓库内部还有 `JmAlbum/JmAlbumMeta → retrofit Response → Comic` 的中间转换，导出则将 `DownloadItem → DownloadComic` 重新构造 Room 实体，仅用于读文件。它们不是立即的功能 bug，但增加字段与转换规则的维护数量。可以在下一次改动这些功能时改成直接领域映射／纯导出输入，不必一次性重写项目。

**A04 · 过度防御主要表现为隐藏失败和保留整包，不是并发控制过多。**

应收敛的例子：F02/F03 把存储失败当默认／成功；备份把部分坏载荷降为空集合；[DownloadExportViewModel.kt:86](/Users/utolaris/Documents/ai/jmcomic-plus/app/src/main/java/com/par9uet/jm/ui/viewModel/DownloadExportViewModel.kt:86)把所有统计异常静默忽略，导致权限错误和真实缺文件无法区分。

[proguard-rules.pro:12](/Users/utolaris/Documents/ai/jmcomic-plus/app/proguard-rules.pro:12)保留整个 coroutines、Retrofit、Koin，以及多个业务包、`j$.**` 等，远超“保留被反射读取的字段”。这是维护债：削弱删除无用代码和优化能力，也使新增类自动落入大范围保留。已有 release JSON 字段检查，可据此逐步收窄；不能直接删除所有 keep 规则。

应保留的保护：会话代次及候选登录隔离、统一的锁顺序、下载单写入者门闩、缓存迁移先复制后提交、图片临时文件与完整性检查、缓存代次和租约、取消异常传播。它们针对真实并发与 IO 边界，不宜因看起来复杂就删掉。

**A05 · 可读性问题集中在职责跨度与重复样板。**

`LocalSettingScreen` 约 880 行、`ComicDetailScreen` 约 826 行、`BackupRestoreScreen` 约 777 行，阅读器、收藏工具栏和多个弹窗宿主也较长。多数篇幅是 Compose 布局，不能按行数直接认定架构错误。建议按有稳定输入输出的对话框／展示区块提取，优先处理同时包含状态判断、系统入口和布局的部分。

`LocalSettingManager` 同时实现约 16 个设置相关接口，并用手工监听器逐个投影状态。接口收窄是有价值的，但状态发布、持久化结果和功能规则集中在一个类里，已经促成 F02/F03。优先建立明确的读写结果与一次提交语义，再考虑拆职责；不要给每个 setter 再套一层 use case。

## 未认定为漏洞的检查结果

- 主网络安全配置禁用明文流量，发布版系统 CA 与调试版用户证书规则有区分。没有在检查的主源码或 JMComic 1.1.8 HTTP builder 中发现“信任全部证书／忽略主机名验证”的实现。DoH 明确可选信任用户证书，不应误报为无条件绕过 TLS。
- `FileProvider` 未导出，共享路径限定在更新缓存目录；签名密码由环境变量提供，没有把该机制认定为硬编码密钥泄露。
- 收藏动态 SQL 将用户搜索、标签与账号参数绑定；内部拼接的 SQL 结构不直接等于注入漏洞。
- 旧 ZIP 解压将文件名截为末级名称，并使用临时目录提交；没有把一般性的 `../` Zip Slip 套用到这一实现。解压资源上限仍可作为后续加固项。
- APK 更新缺少应用内独立摘要校验可以改进，但下载经过 HTTPS，Android 安装器也会校验更新签名；没有据此声称攻击者可以无条件替换现有应用。
- 没有把 `API_TOKEN_HASH`、协议解密常量或旧依赖版本本身直接认定为账号密钥泄露／已知漏洞。

## 建议修复顺序与验收

1. **先保证保护和账号边界：F01、F02、F03、F07。** 验收包括备份篡改被拒绝、密钥暂时不可用时不能按无锁进入、保存失败不能显示安全设置已生效，以及 A 批次在 B 会话下零次提交。
2. **再统一失败边界：F04、F05、F08。** 畸形响应返回可重试错误；畸形备份读取阶段失败；配置文件写入失败不能留下不可重试的完成态。
3. **补齐运行与隐私一致性：F06、F09、F10、F11、F12。** 账号切换清空旧分页；阻塞读取立即响应取消；系统备份规则覆盖新文件；所有非 bootstrap 请求遵守 DNS 策略；读取阶段执行大小限制。
4. **最后偿还维护债。** 切断通知工具到入口的依赖环、移除空 Cookie 清理端口、修复依赖扫描口径、删改误导注释、逐步收窄混淆保留规则。避免再做一轮仅移动目录或增加转发接口的重构。
